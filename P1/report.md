## 1. Autotuner 的三个接口

### 1.1 框架与执行流程

本项目用 Python 实现调优调度，C 程序保留矩阵计算。老师规定的参数空间只有 20 个组合，搜索方法所需的操作主要是选择配置、取得耗时、接收反馈，因此自行实现一个轻量框架，便于直接说明三个接口怎样协作。没有引入 OpenTuner 的完整框架；这里着重比较自己实现的 Grid、Random 和 Greedy。

![Autotuner 框架设计](images/framework.svg)

图中的三路输入分别交给 [autotuner.py](src/autotuner.py) 中的 `TargetProgram`、`ConfigSpace` 和 `SearchStrategy`。目标接口知道怎样调用程序，配置接口知道有哪些合法组合，搜索接口决定下一项测什么。它们在 `Evaluator` 处汇合：同一个配置不论由哪种算法提出，都经过相同的编译、运行和评分过程。

以一次 `s=64/O2` 的评估为例，搜索算法先返回包含这两个值的 `Config`。`Evaluator` 检查它属于输入空间，再让 `TargetProgram.build("O2")` 取得对应可执行文件；随后启动新进程，以命令行参数 `64` 传入分块大小。目标程序完成乘法后输出内核耗时，调优器解析这个值，保存该次运行，并把评分交给 `observe()`。搜索算法收到反馈后才能提出下一项。

对于三种基础算法，主循环的关键部分是：

```python
config = strategy.suggest()
trial = evaluator.evaluate(config, trial_id)
strategy.observe(config, trial["score"])
```

`search()` 在这个循环外控制预算、停止条件和最终返回。这样，算法代码不用各自重写编译命令，也不用各自选择计时区域；算法之间的区别来自选点规则，而不是调用目标程序的方式。

### 1.2 目标程序接口

`TargetProgram` 接收目标 C 源码、编译器和公共编译选项。`build(opt)` 为指定优化级别准备可执行文件，`measure()` 负责启动进程并解析输出。程序调用约定很简单：可执行文件接受一个分块大小，第一行输出以秒为单位的乘法耗时。本项目目标还输出 checksum 和内核起止纳秒，便于分别检查结果是否被使用、计时范围是否一致。

优化级别会改变机器码，分块大小则在程序启动时才传入，因此构建按 O0—O3 分开，同一构建能运行五个不同的 `s`。复用构建前会核对源码、编译器、实际编译选项和文件内容，避免设置变化后误用旧程序；复用的只是可执行文件，每次性能测量仍从新进程开始，重新初始化 A、B、C。

运行结束后，接口同时检查退出码、输出格式和时间值。对于本项目的目标，整数纳秒端点应包围乘法循环，并落在同一 RAW 时间域的目标进程区间之内；端点差也应与首行的六位小数耗时相符。超时、非零退出、缺失输出、NaN、零耗时等情况都不能成为更优结果，防止搜索把一次没有正常完成的计算误当作最快配置。

### 1.3 配置空间接口

`ConfigSpace` 接收两个候选列表：分块大小和优化级别。它检查分块值是否为正整数、优化级别是否属于 O0—O3，以及列表是否重复或为空，再生成二者的笛卡尔积。目标程序还会按自己的矩阵大小检查分块上界；本次指定的五个值都在有效范围内。

配置集合和访问顺序分别处理。`ConfigSpace.configs` 提供稳定的“分块在外、优化级别在内”的顺序，Grid 直接使用它，Random 可在它的副本上打乱，Greedy 则通过 `neighbors()` 查询相邻配置。这样，改搜索方法不会改变配置含义，也不用重新拼装编译和运行参数。

这里的“相邻”按候选列表定义，而不是按数值加减。分块列表中的 24 与 64 相邻，优化列表中的 O1 与 O2 相邻；一个邻居只改变其中一项。例如 `s=24/O2` 的邻居是 `s=16/O2`、`s=64/O2`、`s=24/O1` 和 `s=24/O3`。这一约定决定了 Greedy 能沿哪些方向移动。

### 1.4 搜索算法接口与统一评估

`SearchStrategy.suggest()` 提出下一项配置，找不到下一项时返回 `None`；`observe(config, score)` 接收刚测得的评分。Grid 和 Random 保存已访问项，Greedy 还保存当前点及邻居的反馈。算法只使用本次搜索中已经取得的测量，不知道完整配置表中哪项最快。

`Evaluator` 将一个配置变成可比较的评分。若设置重复运行，它会取得各次内核时间，在全部重复均有效时使用中位数；某次失败则该项不评分。日志保留配置、原始输出、样本和耗时，既能解释返回结果，也能把中断前已完成的工作保留下来。预算统计的是配置评估次数，失败也占一次；下面的搜索实验设置每项只运行一次，所以评估次数同时就是目标调用次数。

![调优接口的调用与矩阵计算代码](images/interfaces-kernel.png)

截图中的 `suggest → evaluate → observe` 对应框架图的提议和反馈两条路径。上方六层循环是所有配置共用的计算内核，底部候选复测代码则是在相同评估过程上改变预算分配，具体结果放在第 4.5 节。

### 1.5 优点和局限

这套分工使搜索规则与程序执行分开：增加一种选点规则时，可以沿用已有的目标接口、重复测量和失败处理；更换分块候选时，也不用修改 C 程序或编译流程。编译参数与运行参数分开后，只需准备四个构建即可覆盖 20 个配置，三种算法又共用测量代码，比较条件较容易保持一致。

它的适用范围也比较明确。新目标程序必须按约定接收参数和输出耗时，不能直接输入任意源码就自动识别应调什么；当前调优串行执行，慢配置会占用较长时间。20 项离散空间足以观察三种算法的差别，但还不能代表高维连续参数问题。统一评估消除了调用方式的差异，却不能消除系统波动，Greedy 尤其可能被一次偏低的观测引向别处。

## 2. Matrix Multiplication 目标程序

### 2.1 原程序的计算结构

[老师提供的原程序](src/matrix_multiplication.original.c) 定义了 `n=4096`，使用三个 `double` 数组 A、B、C。初始化逐项用 `(double)rand() / (double)RAND_MAX` 生成 A 和 B，把 C 置零，再计算 `C=A×B`。每个配置都计算相同规模的矩阵；分块只改变访问顺序与循环分组，不改变需要累加的乘积。

六层循环的外三层 `ih、jh、kh` 沿行、列和点积方向按 `s` 前进，确定当前块的位置；内三层 `il、kl、jl` 枚举块内元素。最内层沿 `jl` 扫描 B 和 C 的一段行，对固定的 A 元素完成一组更新。与直接逐个元素做完整点积相比，这种安排把一部分数据访问集中在当前块内，`s` 因而同时影响块循环次数和每次使用的数据范围。

尾块边界判断原本就在老师代码中，我们保留并检查了这一部分。内层既要求索引小于 `s`，又要求块起点加局部索引小于 `n`。例如 `4096=170×24+16`，`s=24` 时最后一块只有 16 个有效位置，三个方向都由各自的边界判断限制，既不会遗漏末端元素，也不会越界访问。第 1 节的代码截图中可以直接看到这些条件。

### 2.2 为调优器做的适配

[运行目标](src/matrix_multiplication.c) 保留了原初始化、数据类型、矩阵规模和六层乘加循环，修改集中在参数和输出。原程序用 `assert(argc==2)` 与 `atoi()` 读取分块大小，适配后检查参数数量，用 `strtol()` 确认整个字符串是有效整数，并检查 `1≤s≤n`。错误输入能够直接返回失败，调优器不用等到计算结束再判断配置是否可用。

计时仍只包围原乘法循环。开始和结束时间先按整数纳秒相减，再换算成秒，首行继续输出可解析的六位小数；起止纳秒也在计算后输出。调优器因而既能读到评分，也能检查输出的秒数是否对应记录的区间。

checksum 对 C 的全部元素求和，放在结束计时之后。它使程序使用计算结果，也给输出增加一个可检查的数值；放在计时后则避免把额外遍历 C 的开销计入乘法性能。相同 checksum 不能说明每个元素都正确，所以数值检查另用参考点积完成。

### 2.3 正确性检查

先在小矩阵上逐元素比较，再在正式规模上检查预定位置。小矩阵版本从目标源码生成，缩小 `n`、增加不同测试输入和参考计算，保留同一个乘法循环；这样可以遍历所有输出元素，发现某个分块或优化级别造成的漏算、重复累加或边界问题。参考值用独立的未分块点积计算，先将 A、B 元素转为 `long double`，再用这个类型完成乘法和累加，减少参考计算自身的舍入误差。

小矩阵取 `n=128` 和 `129`，分别包含可整除与不能整除分块的情形。输入除三组正数随机矩阵外，还包括两组含正负值的矩阵，以及单位 A 和具有确定结构的 B：正负输入能检查有抵消的点积，单位矩阵输入则容易判断输出应等于 B。两种规模、五个分块、四个优化级别和六组输入组合成 240 个逐元素用例，全部满足误差条件。

误差采用 `|C−参考值|≤10⁻¹²+10⁻¹¹×|参考值|` 判断，同时记录最大绝对误差和相对误差；相对指标的分母为 `max(|参考值|,10⁻¹²)`。对于接近零的参考值，相对指标可能被放大，因此是否合格仍按上面的误差条件判断。不能只看某个相对误差数字，也不能要求浮点结果与高精度累加逐位相同。

为检查内存和未定义行为，另在 `n=129/O1` 下为五种分块打开 AddressSanitizer 和 UndefinedBehaviorSanitizer。129 不能被任何一个候选分块整除，因此每项都会走到尾块；五个用例均完成全元素检查，没有 sanitizer 报错。数值比较负责发现结果不符，sanitizer 则补充检查内存访问和未定义行为。

正式规模没有再计算一套完整的未分块参考矩阵，而是选 `s=24/O0` 和 `s=128/O3` 两个代表配置，各检查 24 个位置：包含边角、中心和尾部附近的八个位置，以及 16 个固定伪随机位置。前者包含长度为 16 的尾块，后者覆盖完整大块及最高优化级别，两个检查都保留正式目标的原初始化。

| 检查 | 比较范围 | 最大绝对误差 | 最大相对误差 |
| --- | --- | ---: | ---: |
| 小矩阵 240 个用例 | 每例全部元素 | 5.174333×10⁻¹⁴ | 7.569939×10⁻¹² |
| `n=4096，s=24/O0` | 24 个预定位置 | 2.937539×10⁻¹² | 2.814528×10⁻¹⁵ |
| `n=4096，s=128/O3` | 24 个预定位置 | 2.937539×10⁻¹² | 2.814528×10⁻¹⁵ |

大矩阵两个配置的抽查均满足误差条件。这支持所查位置的数值正确性，与小矩阵的全元素检查互为补充，但不等于证明 4096×4096 的每个输出都正确。

### 2.4 性能计时

原程序用 `gettimeofday()` 计时，在当前 WSL2 环境的前期运行中，它给出的内核时间曾大于 Python 单调时钟记录的整个目标进程时间。这里比较的是不同时间域，不能把差值直接解释成计算错误，也不能用一个比例换算后混入配置表。为选定测量基准，我们将 Linux `CLOCK_MONOTONIC_RAW` 与宿主 QPC 的对应区间比较，检查覆盖空闲等待、固定次数 CPU 工作量，以及 `s=128/O2` 和 `s=8/O0` 两种快慢矩阵运行；宿主读数前后分别读取 Linux 时间，使用实际边界限制通信带来的不确定范围。

这些对齐区间中的 RAW 与 QPC 读数一致，因此乘法内核、目标进程和搜索总耗时均采用 `CLOCK_MONOTONIC_RAW`。正式实验块前后继续检查对应区间，`MONOTONIC`、`REALTIME` 只保留作辅助读数；内核和进程包含关系也在同一时间域内检查。有限对齐只支持这次测到的区间，不能保证未采样时刻的精度，更不能解释同一构建在不同时段的全部性能波动，所以重复样本和慢样本都保留。

## 3. 配置参数值组合

### 3.1 循环分块大小

分块候选为 `s∈{8,16,24,64,128}`，属于运行时参数。改变 `s` 会同时改变外层三重块循环的步长和内层三个局部索引的上界，程序仍完成相同的矩阵乘法。小块会更频繁地进入下一块、计算块位置和检查边界，大块则扩大一次处理的数据范围。

分块大小可能影响循环控制开销和数据局部性，这两个因素不一定随 `s` 同方向变化。因此不预先假定“越大越快”，而是测完五个候选；24 也有必要保留，它能覆盖不整除 4096 的情况。性能差异由结果表分析，数值完整性由前面的边界和参考计算检查。

### 3.2 编译优化级别

优化候选为 `O∈{O0,O1,O2,O3}`，属于编译时参数。四级共同使用 `-std=c11 -Wall -Wextra`，只有 `-O0` 至 `-O3` 不同，没有加入并行、BLAS 或其他计算实现。每个优化级别生成一个可执行文件，再把五种 `s` 逐项传入，共得到 5×4=20 个配置。

这样安排能分别观察编译优化与分块的影响：同一列中机器码相同、运行参数不同；同一行中分块相同、优化构建不同。编译耗时不进入乘法评分，搜索成本中则保留实际发生的构建检查和调度开销。

### 3.3 实验条件与统计方式

所有正式性能比较使用 `n=4096`，串行运行并固定亲和性到 WSL2 逻辑 CPU 0。完整配置测量分三轮，每轮覆盖全部 20 项，访问顺序按预定 seed 随机打乱，用来减轻固定顺序与时段变化的关联；每项每轮启动一次新进程。预热和轮间固定配置观察另记，不加入 60 个配置样本。

下文完整配置表使用每项三个内核耗时的中位数，同时保留最小值、最大值与样本本身。范围描述实际测到的波动，不是置信区间。在线搜索统一最多八次评估、每项一次测量、每次目标超时 1200 秒，各算法独立运行并只使用自己的反馈；多组算法的执行位置作平衡安排，避免某一种算法总在同一先后位置运行。

## 4. 三种参数值搜索算法

### 4.1 Grid Search 与完整 20 配置

Grid 的实现按配置列表逐项提出未访问项，评分影响最终返回，但不改变下一项顺序。它完整遍历后可以对全部候选作比较，代价是需要把慢配置也测完。完整配置实验采用第 3 节的三轮遍历，五种分块和四个优化级别均有三个样本，内核耗时中位数如下。

| s | O0（秒） | O1（秒） | O2（秒） | O3（秒） |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 391.019060 | 101.839140 | 100.628924 | 101.957034 |
| 16 | 314.702166 | 63.628636 | 62.537484 | 64.712676 |
| 24 | 287.353034 | 65.436714 | 63.718468 | 63.927611 |
| 64 | 248.731089 | 55.894518 | 57.380079 | 57.015349 |
| 128 | 236.404080 | 47.395634 | 47.516251 | 47.007504 |

![分块大小与优化级别的实测耗时](images/grid_median.png)

图右侧的横线表示三个样本的最小值到最大值。各项原始样本、中位数、范围与 MAD 见[配置统计表](results/goal2r_summary/grid_summary.csv)；例如 `s=24/O0` 的范围为 238.978801—291.588661 秒，比部分配置宽得多，只看一个中位数会遗漏这一现象。

**O0 与优化构建的差异最大。** `s=8` 时 O0 约 391 秒，O1—O3 约 101 秒；`s=128` 时 O0 仍约 236 秒，优化构建约 47 秒。正式构建的反汇编中，O0 在内层反复从栈中读取索引、计算数组地址，O1 已把部分索引和地址推进放到寄存器及指针递增中。这与优化后控制和地址计算开销减少的方向相符，但仅凭静态汇编不能把全部时间差分解成各类开销的百分比。

**增大分块通常改善耗时，但没有简单的单调规律。** O1—O3 从 `s=8` 到 16 明显下降，继续到 64 和 128 后总体更快；但 `s=24/O2` 的中位数 63.718468 秒高于 `s=16/O2` 的 62.537484 秒，O1 也出现相同方向的反例。块变大减少外层块循环的切换，同时改变 B、C 在块内反复访问的范围，这些机制能说明为什么分块是值得调节的参数。实验没有取得 PMU cache miss 数据，不能据此认定某个配置提高了多少缓存命中率，也不能把一次耗时反转全归因于缓存。

**O1、O2、O3 之间的细差需要结合波动看。** 在三轮中位数中，`s=128/O3` 最小，为 47.007504 秒；O1 和 O2 分别高 0.826% 与 1.082%。三项的范围如下：

| s=128 的优化级别 | 中位数（秒） | 样本范围（秒） |
| --- | ---: | --- |
| O1 | 47.395634 | [46.701970, 53.234821] |
| O2 | 47.516251 | [46.134434, 54.389251] |
| O3 | 47.007504 | [46.822599, 49.688403] |

三个范围重叠，而且正式 O2、O3 构建在两个计时调用之间的机器码完全相同，内核使用标量乘加。因而表中的先后不能解释为“O3 通过 SIMD 稳定胜出”，也不支持“128/O3 是唯一稳定的全局最优”。可以确定的是，在这次完整三轮测量的中位数中它最小，后续用它作为共同参照配置。

### 4.2 Random Search

Random 将 20 项配置复制后按 seed 打乱，每次取尚未访问的一项，因此八次预算对应八个不同配置。它不需要假定相邻配置的性能接近，也能较早跨到大分块区域；另一方面，只有在实际访问并测量后才知道某项是否好，不同 seed 会给出不同的覆盖范围和顺序。seed 使访问顺序可以复现，不会使目标运行时间不变。

以 seed `804730` 为例，八项实际访问如下：

| 次序 | 配置 | 在线内核耗时（秒） |
| ---: | --- | ---: |
| 1 | s16/O3 | 68.604857 |
| 2 | s64/O1 | 60.868061 |
| 3 | s128/O2 | 61.620885 |
| 4 | s24/O2 | 66.964773 |
| 5 | s24/O3 | 63.972597 |
| 6 | s8/O1 | 101.589824 |
| 7 | s128/O0 | 260.528549 |
| 8 | s24/O0 | 285.390572 |

这次既尝试了大分块的优化配置，也花时间运行了两个较慢的 O0 配置。它已经访问完整表中更快的 `s128/O2`，但该项当时测得 61.620885 秒，略高于 `s64/O1` 的 60.868061 秒，所以返回后者。有限预算的波动不只来自漏掉好配置，也可能来自已经覆盖的配置在当时排名不同；算法按照自己的观测选择，没有使用完整表来纠正结果。

### 4.3 Greedy Search

Greedy 默认由 seed 从 20 项中选择一个起点，先测起点，再测当前点所有尚未测过的邻居。邻居按第 1.3 节的规则一次只改一个参数，访问次序沿用配置列表。邻居收齐后，在当前点和邻居中选择评分最小者，只有严格更快才移动；已测过的邻居直接复用反馈。当前点没有更快邻居时停止，若预算先耗尽，则返回所有已测配置中的最好项。

每个起点和邻居试探都占预算，不能只把移动次数当作算法成本。它也不会从一个局部点直接跳到任意配置，例如 `s=24/O2` 不能一步跳到 `s=128/O3`。因此少量测量可能集中在一个局部区域，起点和邻域中的单次观测都会影响路径。

为了观察起点的作用，另用四个固定起点，各自独立运行一次搜索，仍各给最多八次调用。下表差距表示返回配置在完整表中的中位数相对 `s128/O3` 高多少。

| 固定起点 | 返回配置 | 相对共同参照的差距（%） | 调用数 | 搜索总耗时（秒） |
| --- | --- | ---: | ---: | ---: |
| s8/O0 | s16/O2 | 33.037 | 8 | 1277.002 |
| s16/O1 | s16/O2 | 33.037 | 8 | 890.196 |
| s24/O2 | s24/O2 | 35.550 | 5 | 337.954 |
| s128/O3 | s64/O2 | 22.066 | 7 | 497.373 |

从 `s128/O3` 开始的轨迹尤其能说明问题。访问次序和当前点移动不是同一件事：算法总共访问七项，当前点只经历 `s128/O3 → s128/O2 → s64/O2` 两次移动。

| 次序 | 访问配置 | 在线内核耗时（秒） | 在搜索中的作用 |
| ---: | --- | ---: | --- |
| 1 | s128/O3 | 74.612751 | 起点 |
| 2 | s64/O3 | 75.057174 | 起点的分块邻居 |
| 3 | s128/O2 | 72.430840 | 起点的优化邻居；收齐后移动到这里 |
| 4 | s64/O2 | 64.407111 | 新当前点的分块邻居 |
| 5 | s128/O1 | 71.901829 | 新当前点的优化邻居；收齐后移动到 s64/O2 |
| 6 | s24/O2 | 68.217666 | s64/O2 的分块邻居 |
| 7 | s64/O1 | 65.721267 | s64/O2 的优化邻居；收齐后无改善，停止 |

在 `s128/O2` 处，先前 `s128/O3` 的观测已经存在；在 `s64/O2` 处，`s128/O2` 与 `s64/O3` 也已经测过，因此无需重跑这些邻居。在线记录中 74.612751、72.430840、64.407111 秒依次降低，移动符合代码规则；但完整表中终点比起点慢 22.066%。这说明接受一次观测更快的邻居，并不能保证配置的重复性能改善；单次波动与局部访问范围在这条路径上共同发挥作用。

### 4.4 三种算法的比较

算法比较关注两个问题：返回配置在同一张完整配置表中处于什么位置，以及取得这个结果花了多少搜索时间。为避免只选择有利的一次随机运行，使用六个预定 seed 分别运行三种算法。Grid 不使用随机 seed 改顺序，这六项是同一固定前缀在不同实验组中的运行；Random 使用 seed 决定顺序，Greedy 使用它决定起点。

比较中的 Grid 给八次预算，只访问 `s=8、16` 的前八项；它与第 4.1 节的完整 20 项实验必须分开理解。八次 Grid 能保证这八项都被尝试，却没有机会看到 24、64、128。完整 Grid 的优势是覆盖所有候选，在当前小空间中也最便于详细分析；预算截断后，这个保证只剩对前缀的覆盖。

返回配置的共同参照差距定义为：

`g_ref(c)=100×(T_ref(c)/min(T_ref)−1)`

其中 `T_ref(c)` 是完整表中配置 c 的三轮中位数。相同配置取得相同差距，这样不会把不同搜索时段的在线耗时直接当作算法质量；差距为零仅表示返回了该表中位数最小的配置。搜索总耗时则从调优器外测量完整 RAW 区间，包含本次目标运行、构建检查和框架开销；共同构建与搜索后的确认另计。它衡量调优成本，与配置执行一次乘法的时间不同。

| ---: | --- | --- | ---: | ---: | ---: |
| 700001 | Grid | s16/O3 | 37.665 | 8 | 1210.451 |
| 700001 | Random | s128/O1 | 0.826 | 8 | 902.508 |
| 700001 | Greedy | s128/O2 | 1.082 | 8 | 1087.408 |
| 804730 | Grid | s16/O3 | 37.665 | 8 | 1230.572 |
| 804730 | Random | s64/O1 | 18.906 | 8 | 975.438 |
| 804730 | Greedy | s16/O2 | 33.037 | 8 | 1171.882 |
| 909459 | Grid | s16/O3 | 37.665 | 8 | 1505.319 |
| 909459 | Random | s128/O1 | 0.826 | 8 | 1012.337 |
| 909459 | Greedy | s64/O1 | 18.906 | 8 | 912.755 |
| 1014188 | Grid | s16/O3 | 37.665 | 8 | 1069.850 |
| 1014188 | Random | s128/O2 | 1.082 | 8 | 1180.177 |
| 1014188 | Greedy | s128/O2 | 1.082 | 8 | 1012.032 |

这组八次比较中，Grid 的固定前缀主要受枚举顺序限制，而且总会运行两个 O0 配置。Random 能用相同预算分散探索，不过也可能抽到慢项，或错过大分块的优化组合。Greedy 的总耗时中位数最小，其中两组分别在六次和七次调用后停止，实际测量次数少于另外两种算法；它依赖邻域已有改善，起点或局部观测不利时可能停在较差配置。当前结果适合说明这个参数空间中的行为，不能由六组样本推出某算法在任意目标上都最好。

### 4.5 额外尝试：有限候选复测

单次评分可能偏低，因此另外尝试把一部分预算用于候选复测。代码中的 `recheck` 仍给八次调用，前六次按同 seed 的 Random 顺序探索，从成功项中挑出首测最快的两项，最后两次分别复测它们。复测成功后，按各自两个样本的中位数重新排序，两个样本时就是平均值；只有完成成功复测的候选才允许返回，不能继续锁定一个没有复测的首测低值。

这项改动有明确的代价：Random 可以探索八个不同配置，候选复测只探索六个，把另外两次用于更新已有候选的估计。重复测量的动机参考[重复测量研究（2021）](https://arxiv.org/abs/2103.08716)，将返回质量与调优成本分开比较参考[调优算法比较研究（2024）](https://pure.uva.nl/ws/files/182730825/A_methodology_for_comparing_optimization_algorithms_for_auto-tuning.pdf)。这里的 6+2 是本项目的有限尝试，并非论文方法复现；两次测量也不提供统计置信保证。

为了比较返回项本身，六组搜索先分别结束并固定返回，再对 Random 返回、候选复测返回与 `s128/O3` 的并集测三轮。每轮同配置只运行一次，让相同选择引用同一个真实样本，不把两个独立时段的差直接当成配置差。共同确认不反馈搜索，也不计入各算法的搜索总耗时。

逐轮计算 `G=100×(t_Random−t_复测)/t_参照`，分母是该轮 `s128/O3` 的内核耗时。正值表示候选复测的返回项更快，负值表示更慢，单位为百分点；它与按算法搜索总耗时计算的节省比例分别回答质量与成本两个问题。

| seed | Random 返回 | 候选复测返回 | G 中位数（百分点） | 三轮 G 范围（百分点） | 搜索总耗时节省（%） |
| ---: | --- | --- | ---: | ---: | ---: |
| 700001 | s128/O1 | s64/O3 | -6.791 | [-6.984, -3.497] | 39.404 |
| 804730 | s64/O1 | s64/O1 | 0.000 | [0.000, 0.000] | 43.115 |
| 909459 | s128/O1 | s128/O2 | -4.925 | [-14.970, 10.490] | 2.694 |
| 1014188 | s128/O2 | s24/O1 | -49.716 | [-52.106, -48.656] | 6.435 |
| 1118917 | s64/O1 | s64/O3 | -0.263 | [-2.685, 0.137] | 29.242 |
| 1223646 | s128/O3 | s24/O2 | -30.709 | [-30.712, -30.578] | 22.173 |

![有限候选复测的返回质量与搜索成本](images/saved-search-results.png)

六组配对搜索总耗时的节省中位数为 25.708%，表示调优过程较短。同样八次调用不意味着相同耗时：例如 seed `804730` 的 Random 后两项是慢速 O0 配置，候选复测则用这两次运行已选出的较快候选。

第一、第四和第六组的三轮 G 都低于 −2 个百分点，第四与第六组的质量损失尤其明显；第三、第五组的范围跨过这条界限，不能确定质量损失是否在可接受范围内。图中的 −2 个百分点是事先设定的可接受质量损失界限，10% 是搜索成本节省目标，竖线仍是三次实测范围。即使达到成本目标，也不能忽略已经出现的返回质量损失。

第四、第六组说明了探索范围缩小的直接后果：Random 的第八项分别发现 `s128/O2` 和 `s128/O3`，候选复测此时已把预算用在前六项中挑出的候选上，无法再访问它们。不过不能把所有退化都归因于少探索。第四组两次独立搜索都访问 `s64/O1`，首测却分别为 51.620488 和 94.097100 秒，候选排名已经不同；第六组复测又把返回从首测较快的 `s24/O3` 改为 `s24/O2`，两个聚合评分分别为 70.7734605 和 70.417847 秒。

复测确实改变了评分，但没有补回未探索配置，也不足以消除系统波动。本次结果没有支持以这样的质量损失换取搜索时间节省，因此这项方法不值得保留作为改进方案。三种基础搜索仍可分别使用，具体运行命令见 [README](README.md)。
