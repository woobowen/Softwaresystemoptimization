## 2. 2.5 的受限类别是否准确回答

题目要求依据带宽比例判断访存受限或计算受限。当前报告完整给出两个有效带宽及峰值比例，再说明该小尺寸实验存在缓存、行内归约、启动与并行规模等因素，现有证据不足以严格二分。这是对能否由这些数据作分类的明确判断，不是遗漏表格或回避结果；不应为了凑二分而将 52% 或 102% 强行解释为某个硬件瓶颈。

naive 的真实大头是两次归约，占全部 kernel 时间约 75.37%；Triton 减少中间访问与 launch，这些结论都可由代码和 trace 支持。没有 DRAM 计数器或可靠 roofline 证据时，当前限制比武断标签准确。可把“纯访存受限/纯计算受限”的“纯”删去，使措辞直接对应老师问题，不必为此加长说明。

## 3. 三处最小实际修正

1. **2.6 每个 kernel 的处理规模。**“每个 kernel 只处理 100 个元素”字面上覆盖了初始化、递推和最终输出，但最后三个输出 kernel 操作的是完整 100×5000 矩阵。改成“递推阶段每个 kernel 只处理 100 个元素”即可。
2. **2.6 实际计算密度。**“输入遍历减少并没有转化为更高的实际计算密度”暗示已经测过 FLOP/Byte，且暗示当前 eager 实现确实减少 x 的读取。事实上，列内 maximum 和 sub 会各读 x[:,j]，最终输出又读完整 x；框架状态/临时张量读写也必须计入。建议保留“比 naive 计算更多指数”，将末句改为：“状态和临时张量的读写也要计入流量，不能只凭算法的输入遍历次数判断 FLOP/Byte；本次完整调用的开销反而明显增加。”不需要额外实验或重写算法。
3. **Attention 表中 Softmax 的小数。**原值为 17.291451885%，保留三位小数应是 17.291%，而不是 17.292%。独立舍入后分项和可能为 99.999%，总行写 100% 仍合理，不应为了凑和修改某一真实比例。

这三处不改变实验、计算式、结论或截图，只影响表述/舍入。没有发现其他需要为本次复核而扩大修改的实质问题。
